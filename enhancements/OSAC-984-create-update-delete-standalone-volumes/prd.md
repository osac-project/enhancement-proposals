# Create, Update, and Delete Standalone Volumes Through OSAC

## Problem Statement

OSAC can provision storage volumes through its existing storage control plane, but tenants do not have a public way to manage standalone volumes. Tenants cannot prepare storage before provisioning compute, update volume information, or delete unused storage through OSAC. This makes storage dependent on another resource lifecycle and prevents tenants from managing storage as an independent resource.

## In Scope

- Tenants create standalone StorageVolumes through the public API and OSAC console.
- Tenants update editable volume metadata and delete standalone StorageVolumes through the public API and console.
- Volume creation requires a user-provided name, storage tier, size, and access mode.
- Volume names are unique within a tenant, cannot be changed, and remain unavailable until deletion is complete.
- Tenant permissions and ownership rules apply to every volume operation.
- The volume flow shows operation progress and clear errors for invalid or unsuccessful operations.

## Out of Scope

- Viewing and listing volumes through the public API, covered by OSAC-4542.
- Attaching and detaching volumes from CaaS, VMaaS, and BMaaS resources, covered by OSAC-4884.
- Expanding or shrinking volumes.
- Creating, deleting, restoring, or cloning snapshots.
- File and object storage.
- Volume encryption, replication, and storage mobility.

## User Stories

### Cloud Provider Admin

- Not affected by this Feature.

### Cloud Infrastructure Admin

- Not affected by this Feature.

### Tenant Admin

- As a Tenant Admin, I want to create a standalone StorageVolume by providing its name, storage tier, size, and access mode so that I can prepare storage independently from compute resources.
- As a Tenant Admin, I want to update a volume's editable metadata so that I can keep its description and organizational information current.
- As a Tenant Admin, I want to delete a volume that is no longer needed so that I can release its storage.
- As a Tenant Admin, I want volume operations to apply only to my tenant so that one tenant cannot manage another tenant's storage.

### Tenant User

- As a Tenant User, I want to create a standalone StorageVolume by providing its name, storage tier, size, and access mode so that I can prepare storage for my workloads.
- As a Tenant User, I want to update editable metadata on volumes that I own so that I can organize them for my team.
- As a Tenant User, I want to delete volumes that I own so that I can remove storage I no longer need.
- As a Tenant User, I want clear feedback when a request is invalid, unauthorized, or unsuccessful so that I know how to correct it.

## Assumptions

- The storage control plane from OSAC-2872 is available for public volume management.
- Storage tiers and the storage backends they represent are configured before tenants create volumes.
- A volume name is provided by the user and is not generated by the service.
- The public Get/List capability from OSAC-4542 provides volume visibility outside the CUD flow.

## Dependencies

- **OSAC-2872:** Provides the existing storage control plane used by this Feature.
- **OSAC-4542:** Provides public Volume Get/List so users can view volumes outside the CUD operations.
- **Storage tier and backend configuration:** A tenant must have at least one usable storage tier before creating a volume.
