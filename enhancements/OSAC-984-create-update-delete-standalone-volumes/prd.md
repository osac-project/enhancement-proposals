# Create, Update, and Delete Standalone Volumes Through OSAC

## Problem Statement

OSAC can provision storage volumes through its existing storage control plane, but tenants do not have a public way to manage standalone volumes. Tenants cannot prepare storage before provisioning compute, update volume information, or delete unused storage through OSAC. This makes storage dependent on another resource lifecycle and prevents tenants from managing storage as an independent resource.

## In Scope

- Creating standalone StorageVolumes through the public API, CLI, and OSAC console.
- Updating and deleting standalone StorageVolumes through the public API, CLI, and console.
- Applying tenant-scoped permissions to all volume operations.
- Showing lifecycle status and actionable errors to API, CLI, and console users.

## Out of Scope

- Viewing and listing volumes through the public API, covered by OSAC-4542.
- Attaching and detaching volumes from CaaS, VMaaS, and BMaaS resources, covered by OSAC-4884.
- Expanding or shrinking volumes.
- Creating, deleting, restoring, or cloning snapshots.
- Backups and backup management.
- Project-specific volume ownership, sharing, and access-control rules.
- Transferring volumes between tenants or projects.
- File and object storage.
- Volume encryption, replication, and storage mobility.

## User Stories

### Cloud Provider Admin

- As a Cloud Provider, I want tenants to maintain large amounts of data in my cloud so that they are encouraged to use my compute services.

### Cloud Infrastructure Admin

- Not affected by this Feature.

### Tenant Admin

- As a Tenant Admin, I want to manage all volumes in my tenant so that I can administer tenant storage.

### Tenant User

- As a Tenant User, I want to prepare data once and reuse it with compute resources so that I do not repeatedly upload costly data.
- As a Tenant User, I want to choose a storage tier whose cost and characteristics match my workload.
- As a Tenant User, I want to choose an access mode that fits how my workload uses the volume.
- As a Tenant User, I want to create a standalone StorageVolume so that I can prepare storage independently from compute.
- As a Tenant User, I want to update volume metadata so that I can keep my storage organized.
- As a Tenant User, I want to delete a volume that is no longer needed so that I can release its storage.
- As a Tenant User, I want clear feedback when a request is invalid, unauthorized, or unsuccessful so that I know how to correct it.

## Assumptions

- OSAC-984 adds public volume API, CLI, and console flows that use the private storage control plane from OSAC-2872. The private API remains internal and its tenant and credential controls are preserved.
- Storage tiers and the storage backends they represent are configured before tenants create volumes.
- A volume name is provided by the user and is not generated by the service.
- A volume requires a name, storage tier, size, and access mode when it is created. The name is unique within the tenant, cannot be changed, and remains reserved until deletion is complete.
- Storage tier, size, and access mode cannot be changed after creation. The update operation may change `metadata.display_name`, `metadata.description`, `metadata.labels`, and `metadata.annotations`.
- A volume starts in creating and moves to available when creation succeeds.
- A non-retryable creation failure moves the volume to failed. Failed is a terminal creation state; volumes are not retried in place. The API, CLI, and console show an actionable error.
- A failed or available volume can be deleted. Delete moves it to deleting, and successful cleanup moves it to deleted.
- If deletion cannot complete, the volume remains in deleting. The service retries cleanup and reports the latest error to API and console users. The volume name remains reserved until cleanup succeeds.
- Repeating Delete for a deleting volume does not start a second deletion. Deleting an already deleted volume is treated as successful. The name remains reserved until deletion is complete.
- Volumes are tenant-scoped. Tenant Admins can manage every volume in their tenant. Tenant Users can manage volumes in their tenant, and the creating user is recorded for audit but is not the sole owner.
- Project-specific volume ownership, sharing, and access-control rules are not defined by this Feature.
- The public Get/List capability from OSAC-4542 provides volume visibility outside the CUD flow.

## Dependencies

- **OSAC-2872:** Provides the existing storage control plane used by this Feature.
- **OSAC-4542:** Provides public Volume Get/List so users can view volumes outside the CUD operations.
- **Storage tier and backend configuration:** A tenant must have at least one usable storage tier before creating a volume.
